# Architecture decisions (Master Build)

Format: ID, date, decision, reason, consequences. Changes to an accepted decision need a new entry, not an edit.

## ADR-001 (2026-11-08) The Master Specification is the product source of truth
Module numbering follows `docs/product/TWINS_MASTER_SPEC.md`. The Phase 00 audit is a baseline only; the repository wins on any difference (see BASELINE_PRESERVATION_MAP.md).

## ADR-002 Extend, do not duplicate
New concepts reuse existing tables where they fit (`risk_decisions`, `paper_*`, `users`, `accounts`, `broker_connections`, `orders`, `fills`, `positions`). A new table needs a recorded reason in DATABASE_CHANGE_LOG.md.

## ADR-003 Authentication and authorisation
- **Identity:** `users` (existing). Passwords hashed with Node's built-in `scrypt` (no new dependency). Sessions are opaque random tokens stored only as SHA-256 hashes (`user_sessions`), short-lived, revocable.
- **Principals:** a request carries a `Principal`: `user` (id + roles `ADMIN` | `TRADER`) or `system` (named service). The existing shared bearer key becomes the `system` principal used by the frontend proxy only until Stage 09 moves it to user sessions.
- **Roles:** `TRADER` owns private data. `ADMIN` can manage users and read audit but is explicitly DENIED private capital, broker details, orders and positions of other users (Part 4 of the spec).
- **Three enforcement layers:** API (a principal is required on every route), service (`authorize()` / `requireOwner()` from `@twins/types`), and database (row-level security on user-private tables keyed by `current_setting('twins.user_id')`, forced for the runtime role). The frontend is never the only barrier.
- **System actors** (worker, scheduler, approval bot) use separate DB roles; they act for a user only through an explicit `userId` on the job envelope.

## ADR-004 Execution modes and safety boundaries
Three separate modes: `PAPER`, `ASSISTED_LIVE`, `CONTROLLED_AUTO`. Live modes are denied unless every one of: the operator-level live switch (default off, and the existing `LIVE_TRADING` guard still refuses any live configuration), the user's own permission for that mode, a valid per-order user confirmation (assisted) or a policy reference (auto), no active kill switch, and a fresh risk re-check. This is a pure function (`checkExecutionGate`) so it can be tested exhaustively. Nothing in the master build enables live trading.

## ADR-005 AI layer
`AIProvider` stays the vendor-neutral contract. Model output is `Untrusted` and can only enter the system through a structured-output validator; it can never reach sizing, risk limits, permissions or execution. Usage, cost and provenance are recorded per call. No LLM provider is connected before the integrations stage.

## ADR-006 Events and jobs
Every domain event uses one envelope (`id`, `type`, `version`, `occurredAt`, `correlationId`, `causationId`, `userId | null`). `userId` is `null` only for shared platform intelligence. Delivery uses the existing durable outbox and BullMQ queues; jobs carry the same correlation id and an idempotency key built from the event.

## ADR-007 Development fixtures
Until integrations, simulated data comes only from clearly named fixture providers that report `source: "FIXTURE"`; results derived from fixtures are labelled and never mixed into real or live performance. A fixture provider is never a production default.

## ADR-008 Migrations without a local database
Migrations are hand-written SQL plus the drizzle journal, additive only (no drops or rewrites of existing data). With no Postgres available locally they cannot be applied here; they stay IMPLEMENTED, never VERIFIED, until the integration suite runs against them in CI.

## ADR-009 Decision vocabulary
Decision outcome (assessment) and workflow state (lifecycle) are separate columns/concepts, per the spec. Legacy `risk_decisions.status` values map onto workflow states (`APPROVED_FOR_REVIEW` -> `PENDING` with an eligibility flag; `APPROVED` exists only once a human approval is recorded).

## ADR-010 (2026-11-08) Safety allow-list extension for the decision vocabulary
`tests/unit/safety/stopLossCoverage.test.ts` allow-lists every file that names an approval-class state. Two new master-build files name QUALIFIED: `packages/types/src/platform/decision.ts` (vocabulary and state machine only) and `packages/types/src/platform/execution.ts` (the gate only consumes the outcome). Both were added to the allow-list with their reasons. They produce no decision and approve nothing. The producer remains `decide.ts` behind `assertStopLossAllowsEligibility`; when the Stage 07 engine begins to emit QUALIFIED it must route through the same mandatory-stop rule and extend the database invariant first, as the test instructs. Flagged for owner review because it touches a safety test.
(ADR-010 addendum, 2026-11-08) `packages/database/src/schema/userDecisions.ts` is also allow-listed: it holds the CHECK vocabulary for `user_decisions.outcome` and the constraint `APPROVED => QUALIFIED`.

## ADR-011 (2026-11-08) Per-user decisions beside the immutable chain
`risk_decisions` is hash-chained and immutable, so the spec's outcome (QUALIFIED/WAIT/REJECT/EVALUATION_ONLY/NO_TRADE) and workflow state live in a NEW table `user_decisions` (private, row-level secured), linked to the chained row through `risk_decision_id` when a decision came through the existing flow. The chain, its triggers and its API are untouched. Existing `orders/fills/positions` already hang off `accounts` (which pin user and trading mode) and are reused unchanged in Stage 02; their row-level policies need an account join and are scheduled for Stage 07.

## ADR-012 (2026-11-08) Database-level execution lock
`user_execution_permissions` has a CHECK that refuses to record `ASSISTED_LIVE` or `CONTROLLED_AUTO` as enabled. This is defence in depth beside `checkExecutionGate`. Lifting it needs a deliberate new migration after the broker, security, legal and regulatory gates are verified; nothing in the master build does that.

(ADR-011 addendum, 2026-11-08) Review hardening: `user_decisions` is guarded by a trigger and owner-tied foreign keys; a QUALIFIED row cannot be created for a candidate without a positive stop-loss (a floor beneath, not instead of, the `@twins/stop-loss` rule). `tests/unit/safety/qualifiedProducers.test.ts` proves the three ADR-010 files cannot produce a QUALIFIED decision.

## ADR-013 (2026-11-09) Stage 04: research package, AI gateway and Market Context
- **Twelve roles are bound, not rebuilt.** `packages/agents/src/research/specMapping.ts` maps each of the twelve specification roles to the existing agent(s); Calendar & Macro is `market-calendar-v1` + `macro-global-v1`, Research Synthesis is the pure `synthesize` function, Market Context is the new `market-context-v1`. `options-risk-v1` stays registered and scored as an extra specialist. `roleCoverage` reports a missing role or an unmapped agent, so a role cannot disappear silently.
- **Market Context is advisory.** It cannot block and is NOT in `DEFAULT_REQUIRED_AGENTS`: with no regime provider wired it reports UNAVAILABLE (INCOMPLETE in the spec vocabulary) instead of failing the engine closed. A fixture-backed regime is capped at NEUTRAL. Making it required is a deliberate later change once a live regime source exists.
- **The research package is evidence, not a decision.** `buildResearchPackage` carries per-agent spec verdicts (via `toSpecVerdict`), evidence references, agent versions, contradictions, role coverage and a hash, with `grantsApproval: false`. The decision engine keeps its own deterministic gates.
- **One research path for both pipelines.** `ResearchCandidate` mirrors `opportunity_candidates`; `candidateToAgentInputs` produces the same inputs the agents already take. The agents package performs no writes (its guard test stands): `runCandidateResearch` takes an injected sink and the database package supplies `storeResearchPackage`. A candidate has no stop-loss validation yet and is given `null`, never an assumed pass.
- **AI gateway fails closed.** `packages/ai/src/gateway`: provider port (no network in this stage; hosted adapters are Stage 10), fixture provider, prompt registry (versioned, hashed, immutable, refuses variables that could carry message text), routing with fallbacks, bounded retry with backoff, abortable timeouts, error classification, a daily budget that blocks before the call (unknown price or unreadable budget = refuse), and a usage record for every attempt (a record that cannot be stored stops the run). Output leaves only through `parseStructured` as advisory. The gateway imports no database, agent, risk or broker code (pinned by a source test).
- **Usage ledger.** Migration 0035 `ai_usage_records`: append-only, shared-or-owner row-level security, no prompt or response text. Budget is summed over the rows visible in the store's scope.

## ADR-014 — Independent Opportunity Engine (Stage 05, Module 16)
- **Separate package, shared contracts.** `packages/opportunity` holds the engine; it reuses the existing breakout/breakdown/pullback generator (`signals/independent.ts`), the OHLC providers, swing/RSI/candle-pattern helpers, the regime object and `runCandidateResearch`. It has no Telegram, broker, network, order or approval code (a static test pins this) and writes the database only through `packages/database/src/stores/opportunityStore.ts`. A scan produces rows of the SAME `opportunity_candidates` table the Telegram pipeline uses (`source = INDEPENDENT`, origin check unchanged).
- **Scan is pure, the cycle is the only writer.** `runOpportunityScan` takes injected providers and returns drafts plus every skip reason. No universe, no provider, or no usable data is FAILED (never an empty success). Missing/unknown/stale regime is recorded as missing evidence and scored zero; HIGH_VOLATILITY / RISK_OFF suppress candidates for that instrument.
- **Rank is a review order, not confidence.** `opportunity-rank-v1`: explicit factors with points; `confidence: null`, `calibrated: false`, `grantsApproval: false`. Nothing ranks into permission.
- **Stop-loss is a proposal.** The setup's stop is stored with `validated: false`; G-18 stands: the Stage 07 qualification path must run the mandatory stop-loss rule. A candidate without an invalidation level can never be revalidated as valid.
- **Lifecycle lives in the database (migration 0036).** States NEW, IN_RESEARCH, READY_FOR_DECISION, EXPIRED, WITHDRAWN, INVALIDATED, SUPERSEDED. Triggers: start NEW; the thesis (instrument, side, entry, stop, targets, invalidation, expiry, identity) never changes; only legal transitions; finished states are final; ending needs a reason; SUPERSEDED names its successor; every state change writes `opportunity_candidate_events` from the database itself. READY_FOR_DECISION means research finished, not that the candidate is recommended: the package assessment travels with it.
- **Idempotency.** Scans are keyed on (kind, slot) and a FAILED or lease-expired slot is retried; candidates carry a unique dedupe key (instrument, setup, side, timeframe, signal bar, detector version); research claims are `FOR UPDATE SKIP LOCKED`, a failed candidate is not re-claimed in the same run, attempts are bounded, a lost lease is recovered, and a worker cannot resurrect a candidate that was ended while it held it.
- **Dispatch is source-agnostic and resolves the dispatch half of G-17.** Any NEW candidate (either source) is researched through `runCandidateResearch`; the runtime safety check runs first and a refusal stops the batch without using an attempt. Telegram claims are still not materialised as candidates (G-19).
- **Wiring.** Scheduler enqueues one `opportunity_queue` job per cron slot (job id = slot); worker consumes it. Both OFF unless `TWINS_OPPORTUNITY_ENABLED=true`. New scheduler effect `research_intake` is gated by the intake control and kill switch (fail closed) but not by TRADING_ENABLED, because research must run while trading is off. The agents' own gating is untouched (a guard test pins that production agents exist only when the agent engine is enabled); the opportunity providers are loaded separately.
- **Honesty.** Only file/in-memory OHLC and last-price snapshots exist, so every scan is labelled FIXTURE unless the operator declares otherwise; live scanning is NOT operational (G-20).

## ADR-015 — Capital, confidence, risk and simulation (Stage 06, Modules 08-11)
- **Two new packages, existing tables.** `packages/planning` (decimal math, specifications and fees, costs, sizing, risk assessment, simulator, evaluation path) and `packages/confidence` (strength score, calibration). They reuse the Stage 02 tables `user_capital_profiles`, `user_risk_policies`, `confidence_assessments`, `risk_assessments`, `simulations`, `confidence_calibration_runs`, and the existing risk-package governors (drawdown, liquidity). Migration 0037 adds only `risk_control_events` plus a few limit columns, a `verdict` on risk assessments and an owner-keyed link from a simulation to its assessment.
- **Money is fixed-point.** `decimal.ts` (BigInt, 8 decimals). Amounts at risk and costs round UP, profits and quantities round DOWN. The older float-based sizing in `packages/risk` is untouched and still serves the risk-decision flow; the candidate path uses the new engine.
- **Nothing is built in.** Contract values and fee schedules come from versioned providers (memory, file) and carry a source kind (OFFICIAL needs a reference, OPERATOR_FILE, FIXTURE). Anything not OFFICIAL restricts the risk assessment (size x0.5). With no provider, an instrument is BLOCKED (SPEC_UNAVAILABLE), never guessed.
- **Sizing can only shrink.** The budget is min(risk percent of available capital, per-trade cap, daily / portfolio / correlated-group headroom) times a restriction multiplier that must be in (0, 1]. Whole lots are found by binary search so the stop-out loss INCLUDING costs and slippage fits; invariants are re-checked and a violation returns NOT_SIZED. Derivative sales are not sized (no margin model).
- **Risk is deterministic and takes no opinion.** `preflightRisk` + `assessRisk` return PASS / RESTRICTED / BLOCKED with coded reasons, limits, exposure, evidence, policy version, time and corrective actions. Confidence, agent verdicts and preferences are not parameters (a test pins this and scans the source). Missing or stale inputs restrict or block; an unknown portfolio state BLOCKS.
- **Stop-loss.** Structural checks (missing, wrong side, equal, off-tick, wrong basis) block. Every result states `stop.independentlyValidated: false`; the evidence-based mandatory validation remains a Stage 07 qualification-path requirement (G-18 stays open).
- **Confidence is strength, not probability.** `confidence-strength-v1`: ten weighted components in correlated families (a family's positive contribution is capped at its heaviest member), missing evidence scores zero and dilutes toward neutral, caps for missing/halted/contradicted/fixture/stale evidence, provenance (package hash, agent versions, evidence refs). Always UNCALIBRATED with `winProbability: null`. Calibration is separate: CALIBRATED needs at least 200 out-of-sample outcomes, populated monotone bins; only then can a bin rate be read as a probability. The specification's PDF sizing tiers are NOT implemented: confidence has no path into the position size.
- **Controls and recovery.** `risk_control_events` is append-only with row-level security (platform rows visible to all, user rows to their owner). The database enforces the recovery policy: a system actor can never clear a drawdown halt or a kill switch, reasons are mandatory, expiry exists only on SET. The daily-loss halt expires at the next IST day. The global kill switch stays in `system_controls` and the intake gate.
- **Integration.** `runEvaluationCycle` evaluates READY_FOR_DECISION candidates (either source) for every active account with a capital profile and policy, and records halts first. Wired into the worker's opportunity job behind `TWINS_EVALUATION_ENABLED` (off by default). Ownership: every user write goes through `withUser`; composite (account, user) keys prevent cross-user references. No multi-user access is enabled; Stage 01 and G-13 are unchanged.

## ADR-016 — Decision engine, human approval, paper execution and trade management (Stage 07, Modules 12-14)
- **Three packages, one workflow.** `packages/decision` (engine, revalidation, approval, cycle), `packages/execution` (price provider, position rules, paper execution, monitoring, paper portfolio), plus stores in `packages/database`. Candidates of BOTH pipelines enter the same path: candidate > research package > confidence > capital / risk / simulation (Stage 06) > decision > approval > execution > position > outcome. The legacy signal pipeline (risk_decisions, risk_approvals, `packages/paper`, paper_trades) is untouched and keeps working; the master-build path uses new `paper_*` tables and never writes the real broker tables (`orders`, `fills`, `positions`).
- **Decision engine.** Pure and deterministic. Fixed precedence NO_TRADE > REJECT > EVALUATION_ONLY > WAIT > QUALIFIED. Fixture-backed candidates, unverified specifications and a missing PAPER permission can never qualify (EVALUATION_ONLY). Confidence is only a minimum-strength filter that can make the outcome more conservative; the size is always the risk-checked sizing; nothing derived from confidence raises an outcome or a size. Every decision stores the full stop-loss validation, permitted size, evidence references, versions, validity window and an explanation (supporting, missing, contradictory, risk and size restrictions, expiry, what would change it, what would invalidate it).
- **G-18 closed.** Every QUALIFIED path runs the full `packages/stop-loss` validation: (1) the engine always calls `validateStopLoss` on the candidate's own levels and its last statement before the only return is `assertStopLossAllowsEligibility`; (2) the persistence door and migration 0038 refuse a QUALIFIED row without a recorded VALID validation, a non-BLOCKED risk assessment of the same owner and candidate, a permitted size of at least one lot and a research package; (3) approval and every execution re-run the validation. `tests/unit/safety/qualifiedProducerStage07.test.ts` proves there is exactly one producer and that no combination of other evidence yields QUALIFIED without a VALID validation. The two new allow-list entries (engine.ts, tradeExecution.ts) carry reasons; no existing assertion or entry was weakened. `qualifiedProducers.test.ts` previously asserted that no producer of user decisions exists; it now pins that exactly one store calls the database doors and that no source file inserts or updates `user_decisions` directly.
- **The doors.** The runtime role keeps SELECT only on `user_decisions` / `user_decision_events`. Decisions are created, ended, invalidated and approved ONLY through four SECURITY DEFINER functions that act for the user bound to the transaction. APPROVED / REJECTED need a `decision_approvals` row (owner-only, PAPER only, one per decision, append-only, idempotent key, revalidation snapshot with `passed = true` for an APPROVE), inside the window, not invalidated. An approved decision is final in the workflow contract (unchanged); withdrawing it is a separate append-only `decision_invalidations` row that execution and the order guard respect.
- **Execution.** `requestPaperExecution` records a chain of independent checks (ownership, permission, approval, decision state, fresh revalidation, execution gate, kill switch, instrument eligibility) and only then creates the request. Requests are unique per (decision, mode) and per key; the order is keyed; fills are append-only and the database applies each fill to its order (quantity, average price, status); the position is DERIVED from fills and healed by `syncPosition`/`reconcilePosition`. The database re-checks on the order itself: ELIGIBLE request, APPROVED decision, window, no invalidation, total entry quantity within the permitted size, side, opposite-side exits no larger than the open quantity. Live modes: the gate refuses them by construction, the request is recorded REJECTED, and a check constraint makes any non-REJECTED live request impossible. No setting enables a live mode.
- **Trade management.** Pure exit rules (stop breach at the observed price, so a gap fills worse, time / session / expiry exits, a target ladder, breakeven after the first rung, trailing, risk-breach flag) over an explicit `PriceProvider`. Every stop move is validated by the mandatory stop-loss rule against the CURRENT price, may only tighten, and is refused by the database otherwise. Missing, stale, future or malformed prices are `PRICE_UNAVAILABLE` events and alerts, never success. Exits are never gated on the kill switch or an expired decision (only entries are). Closed paper positions write `trade_outcomes` (mode PAPER, tied to the paper position); paper results never mix with real ones.
- **Operation.** Worker: the decision cycle runs after the evaluation cycle (`TWINS_DECISIONS_ENABLED`), the management loop runs on a timer (`TWINS_TRADE_MANAGEMENT_ENABLED`), execution is `TWINS_EXECUTION_ENABLED`; all off by default. Approval cards and notifications are contracts; delivery needs Stage 10. There is no user-facing approval API: without authentication sessions (Stage 01) a route could not know who is approving, so approvals run through the owner-run `decision:control` CLI, which names the user explicitly. Multi-user access remains disabled.

## ADR-017 — Outcome learning and performance analytics (Stage 08, Module 15)
- **Outcomes are facts, kept apart from predictions and decisions.** `outcome_attributions` (migration 0039) ties each paper position to its decision, candidate, source, setup / detector version, instrument, timeframe, channel, costs, planned risk, realised R, holding time, exit reason, stop / target behaviour and the agent versions and evidence references behind it; what was predicted at decision time (strength score, planned reward-to-risk, planned loss) is stored in a separate `predicted` object. The table is append-only with owner-only forced row-level security. PARTIAL means "not final" and carries no exit, R or holding time; FINAL needs a closed position and a recorded trade outcome (a CHECK). A change is a NEW VERSION that names its predecessor and gives a reason (guard trigger): a FINAL record can never be replaced by a PARTIAL one, a correction cannot re-point it at another position / decision / candidate / instrument / mode, and ingestion is idempotent on (position, version). `mode` is PAPER-only by constraint until a live execution exists. Nothing is inferred from a decision; what was not recorded stays in `missing`.
- **Provenance is conservative.** The weakest price source behind the fills decides `data_source` (any fixture price, a fixture candidate, or no recorded source = FIXTURE). Every figure is split into all / validated (non-fixture) / fixture datasets and graded: below the minimum sample = INSUFFICIENT_DATA; any fixture record = NOT_VALIDATED_FIXTURE; otherwise LOW, MODERATE, ADEQUATE by size (a CHECK forbids ADEQUATE below 30). The floors (30) cannot be configured lower. Right now every paper outcome is fixture-backed (no live price source, G-20 / G-29), so no figure is validated performance and the reports say so.
- **Analytics reuse the Stage 03 learning code.** Win-rate intervals, drift detection and the minimum windows come from `@twins/historical` (`computeStats`, `detectDrift`), so there is one drift system. New code adds currency metrics in fixed-point decimals (net / gross / costs, average win / loss, expectancy with a 95% interval above the minimum sample, profit factor, drawdown of cumulative P&L, holding distribution), slicing by strategy / version / instrument / timeframe / regime / exit / stop / target behaviour, like-for-like drift by strategy VERSION, channel, regime and source, categorical distribution-shift checks, pipeline funnels (Telegram and independent kept separate, explicit denominators), agent analytics (association by verdict, never accuracy) and decision quality. Unexecuted decisions get only labelled price-path ESTIMATES (target or stop first, ambiguous bars never resolved favourably, no costs, no currency); there is no P&L for a decision that was not executed.
- **Calibration is the Stage 06 procedure, unchanged.** The pipeline feeds it FINAL, non-fixture outcomes with a confidence score recorded before the position opened (look-ahead excluded and counted), ordered by closing time, with the most recent 40% held out as the out-of-sample set. The 200 held-out minimum, the rising-win-rate requirement and the populated-bins rules live in `@twins/confidence` and are not configurable; the pipeline adds a fit-versus-held-out stability check. A raw strength score is never a probability; a probability is readable only from a CALIBRATED run. The run log is a pooled aggregate (anonymous score / win / time samples).
- **Learning is advisory by construction.** `learning_insights` are append-only, evidence-linked (outcome ids and versions with a hash), reproducible (deterministic key over the exact input set, so re-running adds nothing), and carry scope, subject, count, period, provenance, method, algorithm version, reliability and limitations. The recommendation column accepts only `REVIEW` (a CHECK). The package imports nothing that decides, sizes, approves, executes or changes configuration, never touches learning_versions, playbooks, risk policies, permissions, decisions, execution or controls, and writes only attributions, insights, the calibration run log and its own run record (static tests pin all of this). Any future change to a strategy or playbook must use the existing versioned approval and activation controls. A failure in analytics cannot reach a decision: it runs on its own timer behind `TWINS_LEARNING_ENABLED` (off by default).
- **Jobs.** `runLearningCycle` is one bounded job (ingest > attribute > analyse > drift > insights > reconcile > calibration log) with a lease in `learning_job_runs`: one RUNNING run per job (partial unique index), a lapsed run is marked ABANDONED, a finished run is final, per-user failures are isolated and counted. It needs no market feed. Reconciliation re-derives each FINAL attribution against its recorded outcome and reports a difference as a data-quality finding; it never repairs silently.
- **Contracts, not routes.** `ANALYTICS_ENDPOINTS` defines 11 owner-scoped GET endpoints that require an authenticated session and `analytics:read`, with a typed envelope that always states PAPER, live UNAVAILABLE and the not-validated / not-a-probability notice. No route is registered: the only auth today is a shared bearer token that cannot say whose analytics to return (G-26 / Stage 01).

## ADR-018 — Database ownership and domain integrity (Stage 02, migration 0041)
- **One ownership rule, enforced in the database.** Every table with a `user_id` is owner-only under forced row-level security. The single exception is `user_sessions`: it is looked up by the SHA-256 of a 256-bit secret before any user is known, is never listed and is not exposed by any route. A test scans the live catalog so a new user table cannot be added unprotected.
- **accounts and broker_connections are now row-level protected.** Cross-user listing for the worker and scheduler goes through two SECURITY DEFINER functions that return identifiers only (`twins_list_active_accounts`, `twins_list_active_account_users`); no other path lists accounts across users.
- **Relationships cannot cross users.** Every account-owned table references `accounts(id, user_id)`; 0041 adds the same composite key for `accounts.broker_connection_id`. A broker connection stores only a secret REFERENCE (`secretref:<name>`, format-checked), never a secret.
- **Decision links are pinned to the same user, account and candidate** by a guard trigger (the composite foreign keys of 0033 already pinned the user).
- **Legacy account-owned tables** (orders, fills, positions, portfolio_snapshots) are protected through their account. They are unused by the master-build path (G-28).
- **Derived facts, not stored copies.** `account_portfolio_facts` (allocated notional at entry price, realised P&L, capital) and `paper_position_fill_check` (position quantity versus entry minus exit fills) are security-invoker views over exact `numeric` arithmetic. Margin is not modelled (G-25); no live portfolio source exists (G-22), so nothing is shown as a live balance.
- **Money is exact.** Every price, P&L, capital, notional and cost column is `numeric`; a catalog test rejects any float or integer money column; timestamps are all `timestamptz`.
- **Migrations are forward-only.** Each migration documents its rollback as a NEW migration (never an edit of an applied one).
- Alternatives rejected: RLS on `user_sessions` (would force a user binding before authentication); a GUC-based "platform" bypass policy on accounts (any code could set it).

## ADR-019 — Telegram claims become research candidates (Stage 03, G-19, migration 0042)
- **A candidate is a claim waiting for research, nothing more.** `evaluateTelegramClaim` (pure) turns one stored parsed claim into a NEW candidate or records why not; the shared, source-agnostic research dispatch then claims it exactly like an independent one. Research, stop-loss validation, risk, decision and approval are unchanged and still required; static tests prove the pipeline cannot import or write any of them.
- **Never invent.** A missing stop-loss or target is listed as missing information; a missing strike, option type or entry condition is a refusal (INCOMPLETE), because the candidate contract needs an instrument and an entry kind and "market" would be an invented default. A day-and-month expiry without a year stays null. Nothing is mapped silently: only the supported index options the parser already identifies become candidates; SELL (unresolved intent) is UNSUPPORTED.
- **Only the current revision.** Revision state comes from the existing classifier (`getRevisionStates`). A superseded revision is never a candidate; an edit's candidate is version N+1 and supersedes version N (state SUPERSEDED, `superseded_by`, reason MESSAGE_EDITED, lifecycle audited by trigger).
- **Contradiction is not guessed away.** Impossible level ordering or a conflicting level basis refuses the claim; the opposite view of the same underlying by the same channel within 30 minutes is held (CONTRADICTORY, naming the conflicting candidate). An exact repeat is a DUPLICATE of the active candidate.
- **Validity runs from the message time.** 90 minutes by default (configurable), shortened to the stated contract's last close; a late capture is flagged (DELAYED_CAPTURE, FIRST_SEEN_EDITED) but never extends validity.
- **Every decision is audited.** `telegram_claim_candidacy` is append-only, one row per (claim, policy version); reason codes only, never message text. A new policy version re-evaluates deliberately.
- **Database refusals.** A Telegram candidate needs a stored parsed claim (trigger), a thesis and provenance (check); thesis, timeframe, missing information, provenance and version never change (trigger); one candidate per claim (unique).
- **Telegram data is shared platform intelligence** (ADR-003): channels, claims and candidates have no owner; private trading data stays per user. The read API therefore uses the shared permissions, exposes parsed fields through the existing allow-list and masks channel identifiers.
- **Off by default** (`TWINS_TELEGRAM_CANDIDATES_ENABLED`), bounded per run, stops with the intake control and kill switch, failures isolated per claim (an infrastructure failure is not recorded, so it is retried).
- Alternatives rejected: defaulting a missing entry to "market" (invents a value); creating candidates inside the intake path (couples capture to research); one candidate per message instead of per claim (breaks the existing claim-unique origin rule).

## ADR-020 — Durable outcomes and reproducible analytics (Stage 08 completion, G-49, migration 0046)
- **Status:** accepted 2026-11-11; verified in hosted CI (run 43089021401, commit 444b759). Builds on ADR-017 (outcome learning); changes none of its safety rules.
- **A position is never CLOSED without its trade outcome.** The close, its `CLOSED` event and the outcome commit in ONE transaction. The unique index `trade_outcomes_paper_position_unique` makes "exactly one outcome per position" a database fact; a hand-written pre-flight in the migration refuses to run on data that already violates it. A sweep in the existing worker cycle repairs a CLOSED position that has none (older code, or any other path), so recovery does not depend on the atomic write alone.
- **Attribution writers queue per position** (advisory lock) because the guard trigger can otherwise raise for the loser before `ON CONFLICT` applies.
- **Analytics are served from immutable snapshots, not recomputed per request.** A snapshot is built from one `REPEATABLE READ` read-only transaction; the report is a pure function of those inputs, the analysis settings and the algorithm versions, with its "as of" taken from the evidence (never the clock). `evidence_hash` says whether the snapshot is still current for a user; `input_hash` (adds platform pipeline counts) is the unique identity, so concurrent requests converge on one row. Staleness is explicit (`CURRENT` / `STALE` + reason), never silent.
- **One configuration.** The API and the worker both use `loadOutcomeLearningConfig`; the settings that shape the analytics are part of snapshot identity. The 30-outcome floor and the 200 out-of-sample calibration requirement are not configurable.
- **Corrections stay append-only and operator-controlled.** `outcome-correction` can only re-derive a record from the evidence currently recorded, as a new version plus an audit event in one transaction; dry run by default; confirmation bound to the exact plan.
- **Numbers.** Money and R are 8-place fixed point end to end; no figure is shown below the sufficiency floor; views that need data that does not exist (percent drawdown, signal pattern, MAE/MFE) are explicit NOT_AVAILABLE, never approximated.
- **Alternatives rejected:** a Redis/outbox event for close→outcome (a second system to keep consistent with the database; the outcome row itself is the durable event); repurposing `performance_snapshots` (it has no owner row-level security, no append-only guard and no input identity); computing analytics on read (the original behaviour: not reproducible, not consistent across reads, and expensive); letting the correction command accept new values (would be a direct overwrite path).
