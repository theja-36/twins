## 2. What follows from those facts
* **A remote party could not have delivered the callback.** The listener accepted connections only on the Mac's loopback interface, so the request came from a process on that Mac (a browser or another local program), not from the internet. This rules out an external replay unless a tunnel or port-forward to 8765 existed (nothing in the run created one).
* **The callback proves that this Mac fetched the exact login URL** (the `state` is unguessable and was visible only in the process arguments of `open` and in the browser that received it).
* **The authorization itself was valid**: the exchange succeeded and the server accepted the session, so a real Kite login (or an existing authorised session) stood behind it.

## 3. Hypotheses, ranked
1. **Most likely - an existing Kite web session in the default browser.** `open` handed the URL to the default browser; the browser already held a logged-in `kite.zerodha.com` session for an app the user had authorised before, so Kite redirected straight to the callback without showing a password or TOTP prompt (a documented behaviour of the Connect login for an active session). The tab appears for a moment and then shows the listener's "Login received. You can close this tab" page; it can open behind other windows, on another desktop or in another browser profile and go unnoticed. Consistent with: the sub-95-second total, the matched `state`, the owner's report of no prompt, and the fallback being added right afterwards.
2. **A fast manual login in a window the owner did not register as "a tab"** (password + TOTP in under about 40 seconds, then the rest of the run). Possible but tight.
3. **Another local program fetched the URL** (it could read it from the process list while the run was active) using a browser session or cookies on this Mac. Requires local code execution as the same user; I found no evidence of it, and it would still require a valid Kite session. Cannot be excluded from the retained data.
4. **Remote origin**: excluded by the loopback binding unless a tunnel existed (none was created by the run).

I cannot choose between 1, 2 and 3 from what is retained; the discriminating evidence is outside the repository (browser history, Zerodha account records).

## 6. Design changes already made so that a callback listener is never needed again
* The new `kite-login` (merged in PR #62) uses **no local listener and no automatic browser launch**: the owner opens the printed URL, logs in, and types the `request_token` from the redirect address into the tool through stdin. Every login step is therefore a visible human action and there is no unattended callback path to spoof.
* Because the token is typed by a person, the redirect URL registered in the app can be an inert address (for example a loopback port nobody listens on); the browser then shows a connection error whose address bar holds the `request_token`, which is what the owner copies.
* The one-shot runner of 2026-10-31 must not be reused. It stays outside the repository and is not part of any build.
