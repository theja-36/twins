### Image provenance - what is and is not proven
Proven: the running containers use image id `sha256:ef8b…393c`; that image's labels name the commit and the hash of the exact source manifest it was built from; the manifest was verified against `git archive` of the commit. **Not proven / limits:** the id is a local content id, not a registry digest (images are built on the host and not pushed anywhere, so there is no independent signature or attestation); the Postgres and Redis images are referenced by tag/digest as before; the labels are written by the build script, so they are as trustworthy as root on the host. The old `bot-*`/`capture-*` images carry no commit label. The minimum feasible fix delivered now is the label + `deployments.jsonl` convention above; a registry push with SBOM/attestation is future work.

## 5. Defects found by the real run (fixed)
1. `safety-control` and `audit-verify` in the compose file used `command:`, so `compose run --rm audit-verify --require-ddl-watch` **replaced** the CLI with the flag (`node: bad option`). The same defect made `twins-audit-verify.service` unusable. Fixed: both now use `entrypoint:` (arguments are appended); a unit test (`auditInfra.test.ts`) pins it. The earlier Stage 1 evidence for these services came from local runs, not the compose services - this was the first real container run.
2. `staging.env` had no `TWINS_APP_DB_PASSWORD` and the database had no `twins_app` role: both created as part of this deploy (§3).

## 7. Rollback
Backups and previous state: images `twins-staging:capture-8cb22f9` (api, worker) and `twins-staging:bot-aba762bb` remain on the host; pre-change copies of `staging.env`, `bot.env` and `docker-compose.staging.yml` are `*.pre-main-a0120d75-<UTC stamp>`; the pre-deploy database backup is `backups/pre-deploy-main-a0120d75/…20261029T135224Z.dump.enc` (+ `.sha256`).
**Level 1 - code only (database stays at 0012).** On the host, in `/opt/twins-staging/infrastructure/staging`: `cp docker-compose.staging.yml.pre-main-a0120d75-<stamp> docker-compose.staging.yml`; set `TWINS_IMAGE_TAG=capture-8cb22f9` and `TWINS_BOT_IMAGE_TAG=bot-aba762bb` in `staging.env` (or restore `staging.env.pre-main-a0120d75-<stamp>`); `docker compose -f docker-compose.staging.yml --env-file staging.env up -d api worker`. **Unverified** assumption: the old code runs against the migrated schema (it never updates the now-append-only tables); the old compose gives it the owner credential. Use level 2 if there is any doubt.
**Level 2 - database restore from the pre-deploy backup** (destroys everything written after 13:52 UTC on 2026-10-29, including the synthetic rows):
1. `docker compose … stop api worker approval-bot` (and keep capture stopped).
2. Decrypt: `python3 /opt/twins-staging/offsite/twinsenc.py decrypt /root/twins-offsite-keys/twins-staging-offsite-00fd8fc3.key backups/pre-deploy-main-a0120d75/twins-staging-daily-20261029T135224Z.dump.enc /root/rollback.dump` (mode 0600; the key path is the one in `twins-backup.sh`); verify `sha256sum -c` of the `.enc` first.
3. Restore into a scratch database first and check counts (45 messages, 9 migrations): `docker exec -i twins-staging-postgres-1 sh -c 'createdb -U "$POSTGRES_USER" twins_rollback && pg_restore --no-owner -U "$POSTGRES_USER" -d twins_rollback' < /root/rollback.dump`.
4. Swap (during the stop): `ALTER DATABASE "$POSTGRES_DB" RENAME TO "<name>_post_deploy"; ALTER DATABASE twins_rollback RENAME TO "$POSTGRES_DB";` then apply Level 1, start services, `shred -u /root/rollback.dump`. Keep `<name>_post_deploy` until the owner approves dropping it.
The roles `twins_app` (unused by old code) and the 0009-0012 objects disappear with the restored database; re-apply `approval-bot-role.sql` only if the old schema needs it (it does not).
**Forward-fix preferred:** the migrations are additive; prefer fixing forward unless data integrity is in question.

## 8. Remaining limits
Off-host backup is not installed on the VPS and this pre-deploy backup is local; image provenance is label-based, not signed; the audit anchor file is not mounted into the `audit-verify` container (host path owned by root, container user `node`), so staging runs verify without `--anchor-file` and the anchor protection against a full-history rewrite is not yet active there; no systemd timer runs `audit-verify` on staging (units not installed); `safety-control` identity (`changed_by`) is self-declared; the bot's DB-read path while active, the scheduler as a long-running service, the capture client and the options viewer were not exercised; Level 1 rollback is unverified.
